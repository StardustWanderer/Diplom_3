# Diplom_3 — UI-автотесты Stellar Burgers

Автоматизированные UI-тесты веб-приложения [Stellar Burgers](https://qa-stellarburgers.education-services.ru) в рамках дипломного проекта.

Тесты проверяют основные пользовательские сценарии регистрации и авторизации пользователей, а также переключение разделов конструктора бургеров.

Проект написан на Java с использованием Selenium WebDriver, JUnit 4 и паттерна Page Object. Для подготовки и очистки тестовых пользователей используются REST Assured и вспомогательные API-методы. Для формирования тестовых данных применяется JavaFaker. Результаты выполнения тестов собираются с помощью Allure Report.

Тесты успешно запущены в двух браузерах: **Google Chrome** и **Yandex Browser**. Для каждого браузера подготовлен отдельный HTML-отчёт Allure.

## Технологии

- **Java 11** — язык разработки.
- **Maven** — управление зависимостями и запуск тестов.
- **JUnit 4.13.2** — тестовый фреймворк.
- **Selenium 4.51.0** — автоматизация взаимодействия с веб-приложением.
- **REST Assured 5.4.0** — отправка HTTP-запросов для подготовки и очистки тестовых пользователей.
- **Allure 2.29.0** — интеграция JUnit 4 и REST Assured с системой отчётности (`allure-junit4`, `allure-rest-assured`).
- **AspectJ Weaver 1.9.22.1** — поддержка аспектов, необходимых для интеграции Allure.
- **JavaFaker 1.0.2** — генерация тестовых данных.
- **Gson 2.13.2** — сериализация и обработка JSON.
- **Lombok 1.18.46** — сокращение шаблонного кода в моделях данных.
- **Maven Surefire Plugin 3.2.5** — запуск тестов JUnit в рамках Maven.

## Требования к окружению

Перед запуском убедитесь, что установлены:

- JDK 11;
- Apache Maven;
- Google Chrome и/или Yandex Browser;
- Allure CLI — для генерации и просмотра HTML-отчётов.

Для запуска тестов в Yandex Browser необходим совместимый исполняемый файл `yandexdriver.exe`. В проекте путь к нему задаётся в `praktikum.config.BrowserFactory`:

```java
private static final String YANDEX_DRIVER_PATH =
        "C:/WebDriver/bin/yandexdriver.exe";
```

Если драйвер находится в другом каталоге, измените значение константы.

## Запуск тестов

Команды выполняются из корневой папки проекта.

**Запуск в Google Chrome:**

```bash
mvn clean test -Dbrowser=chrome
```

**Запуск в Yandex Browser:**

```bash
mvn clean test -Dbrowser=yandex
```

Системное свойство `browser` определяет, какой браузер создаёт `BrowserFactory`.

Команда `mvn clean test` очищает результаты предыдущей сборки и запускает тесты. Сырые результаты Allure сохраняются в каталоге `target/allure-results`.

## Allure-отчёты

Готовые HTML-отчёты для сдачи проекта размещены в репозитории:

- `reports/chrome-report/` — отчёт по результатам запуска в Google Chrome;
- `reports/yandex-report/` — отчёт по результатам запуска в Yandex Browser.

Главная страница каждого отчёта — `index.html`.

### Генерация отчёта для Chrome

Сначала выполните тесты в Chrome:

```bash
mvn clean test -Dbrowser=chrome
```

Затем сформируйте HTML-отчёт:

```bash
allure generate target/allure-results --clean -o reports/chrome-report
```

Для локального просмотра отчёта выполните:

```bash
allure open reports/chrome-report
```

### Генерация отчёта для Yandex Browser

Сначала выполните тесты в Yandex Browser:

```bash
mvn clean test -Dbrowser=yandex
```

Затем сформируйте HTML-отчёт:

```bash
allure generate target/allure-results --clean -o reports/yandex-report
```

Для локального просмотра отчёта выполните:

```bash
allure open reports/yandex-report
```

**Важно:** результаты тестирования обоих браузеров по умолчанию записываются в один каталог `target/allure-results`. Поэтому отчёт нужно генерировать сразу после соответствующего прогона, до следующего запуска с `mvn clean`, который удалит прежние результаты.

Каталог `reports/` не следует исключать из Git, если готовые HTML-отчёты должны входить в сдаваемый проект. Вместе с `index.html` необходимо сохранить остальные файлы отчёта, включая каталоги `assets`, `data`, `history` и `widgets`.

## Покрытие тестами

### Регистрация пользователя

Проверяются следующие сценарии:

- успешная регистрация нового пользователя;
- попытка регистрации с коротким некорректным паролем;
- отображение сообщения об ошибке при вводе недопустимого пароля.

### Авторизация пользователя

Проверяются следующие способы перехода к авторизации:

- кнопка «Войти в аккаунт» на главной странице;
- ссылка «Личный кабинет»;
- ссылка «Войти» на странице регистрации;
- ссылка «Войти» на странице восстановления пароля.

Для проверки успешной авторизации тестовый пользователь создаётся через API. После входа проверяется переход на главную страницу приложения.

### Конструктор бургеров

Проверяется переключение между разделами конструктора:

- «Булки»;
- «Соусы»;
- «Начинки».

После выбора каждого раздела проверяется, что соответствующая вкладка становится активной.

## Назначение пакетов

- **`config`** — конфигурация браузеров, базовый URL приложения и пути API-эндпоинтов.
- **`data`** — генерация тестовых данных пользователей.
- **`model`** — модели данных для запросов авторизации и регистрации.
- **`pages`** — Page Object-классы, содержащие локаторы и методы взаимодействия с конкретными страницами приложения. `BasePage` содержит общие настройки WebDriver и явных ожиданий.
- **`tests`** — тестовые сценарии и проверки. `BaseTest` отвечает за создание браузера перед тестом и его закрытие после выполнения.
- **`utils`** — вспомогательные API-методы. `BaseApiMethods` содержит общие настройки REST Assured и интеграцию с Allure, а `ApiMethods` реализует операции с пользователями.

## Архитектурные решения

### Page Object

Для взаимодействия с веб-приложением используется паттерн **Page Object**. Локаторы и действия, относящиеся к конкретной странице, вынесены в отдельные классы. Тестовые сценарии используют методы страниц вместо прямого поиска элементов в тестах.

Общие настройки WebDriver и явных ожиданий вынесены в `BasePage`.

### Выбор браузера

Создание браузера централизовано в `BrowserFactory`. Браузер выбирается с помощью системного свойства Maven `-Dbrowser`. Это позволяет запускать одни и те же тестовые сценарии в Chrome и Yandex Browser без изменения кода тестов.

### Подготовка и очистка тестовых данных

В сценариях авторизации тестовый пользователь создаётся через API перед выполнением теста. После завершения теста выполняется попытка удалить пользователя через API, если сохранён его токен авторизации.

Такой подход сокращает необходимость ручной подготовки учётных записей и помогает не оставлять тестовые данные на сервере.

### Отчётность

Для сбора результатов используется Allure. Интеграция с JUnit 4 подключена через `allure-junit4`, а интеграция с REST Assured — через `allure-rest-assured`. В Maven-конфигурации также настроены AspectJ Weaver и каталог результатов `target/allure-results`.

Готовые HTML-отчёты для двух браузеров хранятся отдельно в каталоге `reports/`.

## Используемые API-эндпоинты

| Метод | Эндпоинт | Назначение |
|---|---|---|
| `POST` | `/api/auth/register` | Создание тестового пользователя |
| `POST` | `/api/auth/login` | Авторизация пользователя через API при подготовке или очистке тестовых данных |
| `DELETE` | `/api/auth/user` | Удаление тестового пользователя |

Базовый URL приложения задаётся в `praktikum.config.Urls`, а пути API — в `praktikum.config.ApiEndpoints`.
